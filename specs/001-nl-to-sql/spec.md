# Feature Specification: Natural Language to SQL Translation

**Feature Branch**: `001-nl-to-sql`  
**Created**: 2025-11-07  
**Status**: Draft  
**Input**: User description: "I want to use the Phi4 model running locally to perform natural language into SQL statements. The Phi4 model will accept an english language statement related to a database and using a known SQL DB schema for that database, propose the SQL that would execute against that database."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Basic Query Translation (Priority: P1)

A developer wants to convert a simple English question about their database into a SQL query without writing SQL manually. They ask a question in natural language against a predefined database schema, receiving executable SQL in return.

**Why this priority**: This is the core functionality - the minimum viable feature that proves the concept works. Without this, there is no product.

**Independent Test**: Can be fully tested by providing a simple query like "show all users" against the predefined schema and verifying it returns valid SQL like "SELECT * FROM users"

**Acceptance Scenarios**:

1. **Given** a predefined database schema and Phi4 model is running locally, **When** user inputs "show all customers", **Then** system returns valid SQL query "SELECT * FROM customers"
2. **Given** a schema with multiple tables, **When** user asks "how many orders were placed yesterday", **Then** system returns SQL with COUNT function and date filtering
3. **Given** a valid natural language query, **When** user requests translation, **Then** response is received within 5 seconds

---

### User Story 2 - Complex Query Translation (Priority: P2)

A user wants to ask complex questions involving joins, aggregations, or subqueries without manually constructing the SQL. They provide sophisticated natural language queries against the predefined schema and receive appropriate complex SQL statements.

**Why this priority**: Advanced capability that adds significant value but isn't required for initial proof of concept. Can be developed after basic queries work reliably.

**Independent Test**: Can be tested by providing queries like "show average order value by customer in the last month" and verifying the SQL includes JOIN, GROUP BY, and date filtering

**Acceptance Scenarios**:

1. **Given** a schema with related tables, **When** user asks "list customers with their total order count", **Then** system returns SQL with appropriate JOIN and GROUP BY
2. **Given** a natural language query requiring aggregation, **When** user requests "average price by category", **Then** system generates SQL with GROUP BY and AVG function
3. **Given** a query requiring filtering and sorting, **When** user specifies conditions and order, **Then** generated SQL includes WHERE and ORDER BY clauses correctly

---

### Edge Cases

- What happens when the natural language query is ambiguous or could map to multiple SQL interpretations?
- How does system handle natural language that references columns or tables not in the predefined schema?
- What happens when Phi4 model is not running or fails to respond?
- How does system handle very long or complex natural language descriptions?
- What happens when natural language includes typos or grammatical errors?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST use a predefined database schema as context for SQL generation
- **FR-002**: System MUST accept natural language queries in English describing desired database operations
- **FR-003**: System MUST communicate with a locally running Phi4 model to perform translation
- **FR-004**: System MUST return syntactically valid SQL statements that correspond to the input natural language query
- **FR-005**: System MUST use the predefined schema context when generating SQL to ensure table and column names match
- **FR-006**: System MUST handle basic SQL operations including SELECT, filtering with WHERE, and simple conditions
- **FR-007**: System MUST provide error messages when natural language cannot be translated
- **FR-008**: System MUST return responses within reasonable time for interactive use (under 10 seconds)

### Key Entities

- **Predefined Schema**: A fixed database structure including table names, column names, data types, and relationships. This schema is embedded in the system and used as context for SQL generation.
- **Natural Language Query**: The English-language input from the user describing what they want to retrieve or know about the database.
- **SQL Statement**: The output SQL query generated by translating the natural language query using the predefined schema context.
- **Translation Request**: Combines a natural language query with the predefined schema context to send to the Phi4 model for processing.
- **Translation Response**: The result from Phi4 model containing the generated SQL or error information.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Users can successfully translate at least 80% of simple natural language queries into valid SQL on first attempt
- **SC-002**: Translation response time is under 5 seconds for 95% of queries
- **SC-003**: Generated SQL statements execute without syntax errors against the target database schema in 90% of cases
- **SC-004**: Users without SQL knowledge can retrieve basic data from a database using only natural language descriptions

### Assumptions

- Phi4 model is already installed and configured to run locally
- Database schema is predefined and embedded in the system (not user-provided)
- Target database uses standard SQL syntax (PostgreSQL, MySQL, or SQLite compatible)
- Natural language queries are in English only
- Predefined schema complexity is moderate (under 50 tables)
- Schema structure is known at development time and does not change at runtime
